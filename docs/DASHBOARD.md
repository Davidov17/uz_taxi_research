# Admin Dashboard

`src/telegram_bot/web/` — a small local web app for the research team: a
FastAPI JSON backend (`web/api.py`) plus a plain HTML/JS/Chart.js frontend
(`web/static/`) that consumes it. No existing HTTP API existed before this
— everything up to now was the Telegram bot and Python-only services
(`StatisticsService`, `ExportService`); this layer is the bridge from a
browser to that data, added specifically for this feature.

## Running it

```bash
uv run uvicorn telegram_bot.web.app:app --reload
```

Then open **http://localhost:8000/** in a browser. `DATABASE_URL` (from
`.env` or the environment) controls which database it reads — same
convention as the bot and the Alembic migrations.

Interactive API docs (auto-generated by FastAPI) are at
**http://localhost:8000/docs**.

## Architecture

```
web/
├── app.py      # FastAPI app factory: mounts /api and the static frontend
├── api.py      # every /api/* route — thin, calls application/ services
├── deps.py     # get_db() dependency (lazily-created session factory)
└── static/
    ├── index.html
    ├── app.js    # fetch()-based rendering, Chart.js charts, no build step
    └── styles.css
```

No business logic lives in `web/`. Every route parses query params into
`StatisticsFilters`/`ExportFilters` and calls an existing application-layer
service — `StatisticsService`, `ExportService`, or the new
`QualitativeService` (individual driver responses, as opposed to
`StatisticsService`'s aggregates). If a number on the dashboard looks
wrong, the bug is in `application/`, not here — the same services back the
Telegram-bot-adjacent code and are independently tested.

One genuinely new piece: `StatisticsService.MultiAppStats.exclusivity` (a
yes/no breakdown of `survey_platforms.is_exclusive`) didn't exist before —
the Platform section needed it and there was no reason to duplicate that
query in the web layer instead of extending the service properly.

## Sections

| Requirement | Where |
|---|---|
| Overview (totals, by city, by platform, by language) | `/api/overview` → Overview tab |
| Driver economics (earnings, trips, hours, commission) | `/api/driver-economics` → Driver Economics tab |
| Driver profile (hours/day bucket, seasonal pattern, driver type, perceived market leader) | `/api/driver-economics` (same endpoint, extended) → Driver Economics tab, "Driver profile" |
| Platform (usage, multi-app, exclusivity, commission, bonuses, cash share) | `/api/platform-stats` → Platform tab |
| City / language / date filtering | Top filter bar, applied to every tab |
| Qualitative (market leader, reasons to join, suggestions, category requirements, employment, bonus descriptions, payout notes) | `/api/qualitative` → Qualitative tab |
| Screenshots linked to a survey | `/api/surveys/{id}/screenshots`, shown in the Raw Data survey detail panel |
| Raw data (individual completed survey) | `/api/surveys`, `/api/surveys/{id}` → Raw Data tab |
| Export Excel / CSV buttons | `/api/export/excel`, `/api/export/csv/{sheet}` → Export tab |

Platform filtering (a bonus beyond the originally requested filters, city
and date) is included too since it makes the Platform tab meaningfully
more useful without conflicting with anything. Language filtering (added
for the multilingual questionnaire) follows the exact same pattern.

## Language filter

`?language=en|ru|uz` on every `/api/*` endpoint that accepts
`DashboardFilters` (`overview`, `driver-economics`, `platform-stats`,
`qualitative`, `surveys`, `export/*`) — scopes to surveys conducted in
that language (`surveys.language`), via `StatisticsFilters.language` /
`ExportFilters.language`. `GET /api/languages` returns the fixed
`[{code, name}, ...]` list the dashboard's filter dropdown is populated
from (static, not DB-backed — the three languages are fixed by the
questionnaire's translation content, not admin-editable reference data
like cities/platforms). The filter is purely a "which surveys count"
scope — no metric's *meaning* changes with it, matching the questionnaire's
language-independence design (see `docs/SURVEY_SPECIFICATION.md`).

## Driver profile

Added to the existing `/api/driver-economics` response (not a new
endpoint — the current questionnaire's driver-level facts belong next to
the earnings/hours/commission figures already there):

| Field | Shape | Source |
|---|---|---|
| `hours_per_day_bucket` | `CategoryBreakdown` | `WorkingStats.hours_per_day_bucket` — the driver's actual structured choice ("7 hrs - 8 hrs", etc.) |
| `seasonal_pattern` | `CategoryBreakdown` | `DriverExperience.seasonal_pattern` — the current questionnaire's structured answer, authoritative |
| `seasonality_text_classification` | `CategoryBreakdown` | `classify_seasonality()` heuristic over legacy free text — illustrative only, kept separate from `seasonal_pattern`, never merged |
| `driver_type_distribution` | `CategoryBreakdown` | legacy `DriverEmployment.driver_type_id` choice (older surveys) |
| `driver_type_employment_text` | `CategoryBreakdown` | `classify_driver_type()` heuristic over the current questionnaire's open-text `employment_text` |
| `perceived_market_leader` | `CategoryBreakdown` | `Survey.perceived_market_leader_platform_id` (legacy platform-pick answer only — the current questionnaire's `market_leader_text` is open text, surfaced as a qualitative feed instead, not tabulated) |

The dashboard's "Driver profile" chart row (Driver Economics tab) renders
all six: `hours_per_day_bucket` and `perceived_market_leader` as single
bar charts; `seasonal_pattern`/`driver_type_distribution` each paired with
their respective heuristic counterpart as a **grouped** bar chart
(`renderGroupedBarChart` in `app.js`) — two visibly separate series on
the same axis, never summed into one bar, so a structured answer and a
best-effort guess about older data are never visually conflated. (The
structured and heuristic label sets don't always align one-to-one — e.g.
`driver_type_distribution`'s "Independent driver"/"Fleet driver" vs.
`driver_type_employment_text`'s lowercase `independent`/`fleet` — a known
cosmetic limitation, not a data-correctness one; see the end of this
document.)

## Qualitative feeds

`QualitativeService.get_feeds()` (`/api/qualitative`) — individual
driver responses, not aggregates. Existing feeds
(`market_leader_responses`, `reasons_to_join_new_platform`,
`improvement_suggestions`, `category_requirements`) were extended, not
replaced: `market_leader_responses` now includes the current
questionnaire's `market_leader_text` alongside the legacy platform-pick
answer; `category_requirements` now includes the current questionnaire's
survey-level `main_category_text`/`category_requirements_text` alongside
the legacy per-platform structured answer. Three feeds are new:
`employment_responses` (`employment_text`), `bonus_descriptions`
(`Bonus.description`, now the current questionnaire's primary bonus-value
answer rather than an optional aside), `payout_notes`
(`Payment.payout_notes`). All seven render through the dashboard's one
existing qualitative-list mechanism, `renderQualList()` in `app.js` —
no new presentation code was written for these, matching the "generic
qualitative-response display" the frontend already had.

## Sample statistics vs. driver estimates — enforced, not just styled

This is the one hard "Important" requirement in the brief, and it's
enforced at every layer, not just in CSS:

- **Backend**: `StatisticsService.driver_estimates` is a structurally
  separate field from `sample_market` and everything else in the report —
  see `docs/STATISTICS.md`. The qualitative API's
  `market_leader_responses` list is documented in
  `qualitative_service.py` as "NOT verified market data."
- **Frontend**: every chart tab carries a visible
  `.sample-note` banner stating the numbers are sample statistics from
  surveyed drivers, with the response count (n=...) shown on every stat
  card and chart legend — nothing is presented as a population-level
  figure. The Qualitative tab additionally opens with a dedicated orange
  `.estimate-banner` ("⚠️ Driver estimates / opinions — NOT verified
  market data") and the "Perceived market leader" panel is visually
  distinct (orange border, a "driver opinion" badge on its heading) from
  the other three qualitative panels, which are drivers describing their
  own situation rather than guessing about the market.

## Screenshots

The bot downloads every uploaded screenshot to
`settings.screenshot_storage_dir` as it's received (see
`infrastructure/storage.py`, added when this project was prepared for
deployment — see `docs/DEPLOYMENT.md`) and records the resulting path on
`Attachment.local_path`. `/api/screenshots/{id}/image` serves that cached
file, and returns a `404` naming the Telegram `file_id` if a particular
download failed (network hiccup, disk full) or the screenshot predates
this feature — the dashboard never pretends an image exists when it
doesn't. The Raw Data survey-detail panel shows a "View image" link next
to each screenshot row only when `cached_locally` is `yes`.

Downloading is deliberately best-effort and non-blocking: if it fails,
the survey submission itself is unaffected (the Telegram `file_id`/
`file_unique_id` are still recorded, same as before), and the failure is
only logged, never shown to the driver.

## Testing

`tests/test_web_api.py` — `httpx.AsyncClient` against the real FastAPI app
(`ASGITransport`, no network), with `get_db` overridden to the same
savepoint-wrapped test session pattern used throughout this test suite.
Covers every endpoint, city/date/**language** filtering, pagination,
completed-vs-draft visibility, the current questionnaire's driver-profile
fields (`hours_per_day_bucket`, `seasonal_pattern`, driver-type
distributions, `perceived_market_leader`) and qualitative feeds
(`employment_responses`, `bonus_descriptions`, `payout_notes`), the 404
cases (unknown survey, a draft survey's code, an uncached screenshot, an
unknown CSV sheet key), and both export formats.
`tests/test_statistics_service.py` covers `classify_driver_type`/
`classify_seasonality` directly, in English, Russian, and Uzbek, plus that
the structured `seasonal_pattern` answer is never overridden by the
free-text heuristic.

**Not covered by automated tests**: the frontend JavaScript's actual
rendering in a browser (this environment has no browser-automation tool
available). `app.js` was syntax-checked with `node --check` and the whole
app (including the new language filter, driver-profile charts, and
qualitative panels) was manually smoke-tested end-to-end with `curl`
against a running server and a real survey driven through
`scripts/verify_production_flow.py` (including the empty-database case —
every endpoint returns clean zero/empty JSON rather than erroring).
Visually confirming the charts and layout in an actual browser before
relying on this for a real research session is recommended.

## Known limitations

- The "Driver type" grouped chart compares two label vocabularies that
  don't fully align (`driver_type_distribution`'s lookup names like
  "Independent driver" vs. `driver_type_employment_text`'s lowercase
  heuristic codes like `independent`) — both numbers are correct, but the
  bars don't visually pair up on a shared category axis the way the
  seasonal-pattern chart's do (those *do* share a vocabulary). Cosmetic
  only.
- `classify_driver_type`/`classify_seasonality` are still heuristic —
  keyword-based, not NLP — and only cover the keyword sets documented in
  `docs/SURVEY_SPECIFICATION.md`; unusual phrasing in any of the three
  languages may come back `"unclassified"` rather than misclassified
  (the deliberately conservative failure mode), but won't be recognized
  either.
